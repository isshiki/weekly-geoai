# ライブラリ更新履歴の保守

日次ニュースから、読者が「何ができるか」「いつ変わったか」を同じAtlasページで追えるようにする。実装コードや全コミット一覧ではなく、重要な機能追加・廃止・互換性・正確性に影響する変更を扱う。

## 保存先

| 対象 | 正本ページ | 区別するもの |
| --- | --- | --- |
| DuckDB | docs/atlas/tools/duckdb.md | 本体とSpatial拡張。比較記事はspatial-sql-engines.md |
| Python Polars | docs/atlas/tools/polars.md | Rust版・Spatial Polars・GeoPolarsの独立した版と機能 |
| MapLibre GL JS | docs/atlas/tools/maplibre-gl-js.md | MapLibre NativeのiOS/Android版 |
| GeoLibre | docs/atlas/tools/geolibre.md | アプリと@geolibre/map、Python/Rパッケージ |
| GeoPandas | docs/atlas/tools/geopandas.md | pandas・Shapely・Pyogrioそれぞれの提供機能 |
| Shapely | docs/atlas/tools/shapely.md | Shapelyの版と内部GEOSの必要版 |

対象一覧にあるライブラリの日次取り込みでは、正本の機能説明と`#release-history`の両方を確認する。他の製品へこの形式を広げる場合も、既存URLを維持し、版体系を混在させない。

追加対象はGeoPandas（表・図形・CRSの管理）とShapely（図形演算）である。TorchGeo・geoai-pyは既存ページで学習・推論の側を案内し、今回の更新履歴の対象拡大とは分ける。

## 日次に更新する手順

1. 公式リリースノートまたは版付き文書で、対象パッケージ・導入版・変更内容を確かめる。日次記事の公開日や収録日を機能の導入日とみなさない。新しい紹介記事でも既存機能なら、年表を新機能として増やさない。
2. 年表の既存行と照合する。基本は1対象・1版につき1行、新しい版を上へ置く。同じ版への追加情報は行を更新する。プレリリース、実験機能、正式化、非推奨、廃止は区別し、正式化時も導入時点を消さない。
3. 版番号の大小で採否を決めない。用途が広がる機能、重要な互換性変更、利用者に影響する正確性・安全性の修正を採用する。軽微な保守は日次だけに残す。GeoLibre 3.5.1の反復・分岐のような機能追加はパッチ番号でも候補になる。
4. 行に「版と公式出典／公開日／変化と使いどころ／状態・移行注意」を書く。公開日はUTCなど基準を明記し、日が分からなければ未確認と書く。確認日は節または行に残し、既存行を未再確認のまま節全体の確認日を更新しない。
5. 現在の機能説明も必要な部分を更新する。古い版の機能を最新版で初めて追加されたように書かず、本体・拡張・別製品を区別する。測定していない性能や未実行の操作はその範囲を明記する。
6. 公式情報を取得できない場合は、確認済み年表に断定して追加せず、日次や更新記録に未確認事項を残す。収録範囲・未調査期間を更新し、掲載がないことを「変更なし」と解釈させない。未確認の最新版を推奨しない。
7. 元ニュースは日次に保持し、Atlasの正本へリンクする。既存の日次の史実を新しい解釈で書き換えない。サイトの更新履歴には変更したページと理由を記録し、既存スクリプトでテキストフラグメントを生成する。

## 月次に整理すること

現在の機能説明と年表の矛盾、実験機能の正式化・廃止、古い移行注意、未確認事項を優先する。調査していない期間を一度に埋めることや、全パッチ収集は必須にしない。表で比較できる更新履歴に装飾図は追加しない。

## 更新時の確認例

- DuckDB 1.5由来のCRS付き型を紹介する新記事：該当行の補足または既存知識へのリンク。新リリース行を作らない。
- Polars本体のGeoParquet入出力：Polarsへ。Spatial Polarsの空間関数として登録しない。
- MapLibre Native iOSの更新：Nativeのページへ。GL JSの年表に混ぜない。
- 同じリリースの再紹介：重複行を作らない。新しい確認事実がなければ年表変更なしでよい。
