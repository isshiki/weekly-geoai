# 開発者向けニュースの追加収集方針

## 目的

既存のビジネス・製品・市場動向の収集を生かし、一般の開発者が地図・POIを使って作れるものと、AIによって開発・分析がどう変わるかを補完する。想定読者と書き方は[編集ガイド](writing-guide.md)に従う。

## 探す題材

| 題材 | 探す内容 |
| --- | --- |
| 地図を作ってみた | 個人のWeb地図、可視化、地域・交通・歴史・防災などの作品と制作記事 |
| POIを使ってみた | 場所検索、施設比較、カテゴリ整理、データ取得・統合の実装例 |
| AIと組み合わせた | 地図アプリの開発支援、自然言語操作、位置情報を使った予測・分類・分析 |
| 開発で困った | 座標、距離・面積、集計、描画性能、API制約などの再利用できる知見 |
| 大きな機能改善 | 新しい用途を開くOSS・ライブラリの変更。細かな保守更新は追い過ぎない |

日本語のZenn・Qiita・作者ブログと、海外の作者ブログ・公式リポジトリ・制作解説を組み合わせる。検索結果やSNSは発見の入口とし、本文・README・作者の説明で確認する。

検索語の例は「地図 作ってみた」「POI アプリ 開発」「MapLibre 個人開発」「地理空間 AI 実装」「map app built with」「geospatial AI project」である。毎回すべてを検索せず、最近の収集で薄い題材を優先する。

## 量と選定

- まず直近7日を探し、良い候補が少ない場合だけ30日程度まで広げる。公開日・更新日・発見日は区別する。
- 保存候補は1回0〜3件を目安とする。見つからなければ0件でよく、件数のために古い記事や類似作品を追加しない。
- 「何が作れるか」「どのデータ・道具を使うか」「読者が持ち帰れる工夫」が分かるものを優先する。画面の見た目だけで中身が分からない場合は、分かる範囲を限定する。
- AIの記載がない地図作品も対象にする。AIとの関係を推測で付け足さない。
- URLと題材をdaily、drafts、Atlasで照合する。同じ作品のSNS・README・ブログを別々の新着として数えず、既存記事に意味のある追加がある場合だけ更新する。
- 特定の作者や技術に偏らないよう、週次選定で出典と用途の重複を見直す。個人作品と、継続運用を前提とするサービスは区別する。

## 確認・保存・報告

公開元、日付、主要機能、必要な環境、コードやデータの利用条件を必要範囲で確認する。公開コードがあるだけでオープンソースと判断しない。動作未検証のデモや企業の効果主張は、その範囲を保持する。

採用した候補はgeoai-save-dailyの手順で日次記録、必要なAtlas、更新履歴へ反映し、検証後にコミット・プッシュする。原文未確認の検索候補を確認済みとして公開しない。日次保存は週刊への採用確定ではなく、木曜に編集ガイドに沿って選び直す。

ユーザーが「今日の分」など日次の記事を渡した際に追加検索する。投稿のない日に独立して実行する自動化は設定しない。記事の修正だけを頼まれた場合や、提供分のみと指定された場合は追加収集を行わない。日次の完了報告で、提供分と追加発見分を区別し、追加なしの場合も簡潔に伝える。
