# 地理空間データの来歴とレコード単位のメタデータ

地理空間データの来歴は、どこから取得し、どう作り、どの変換を経たかを示す情報である。AIが個々のレコードを抽出・再結合する場合、データセット全体に付けた説明だけでは、その情報が結果へ引き継がれないことがある。

## 整備済みデータでも調査時点を引き継ぐ

Praztoは2026年11月9日、Passworkに企業・地域・気象の13データセットを標準搭載したと発表した。法人番号・住所・日付のキーを整備し、自然言語・条件・SQL検索、CSV出力、業務システムへの連携を案内している。

整備サービスの月次・日次更新は、国勢調査などの元データが同じ周期で新しく観測される意味ではない。結合キーがそろっていても、対象区域・単位・調査時点・元の出典を保存し、自社データとのずれを確認する。[提供元の発表](https://prtimes.jp/main/html/rd/p/000000035.000093895.html)（2026-11-10確認。サービス実操作・結合精度は未検証）。


## 入力・処理・出力をつなぐ

W3CのPROVは、データなどの実体（Entity）、生成や変換の活動（Activity）、関与する人・組織・ソフトウェアなどの主体（Agent）の関係で来歴を表す。作成者名だけを付けるのではなく、どの入力から何を経て結果ができたかをたどれるようにする考え方である。

例えば「店舗データのある版 → 対象業種の抽出と区域への結合 → 区域別件数」という流れを記録する。件数だけを保存すると、データが更新されたのか、カテゴリや境界の扱いを変えたのか判別しにくい。

## 最小限の作業記録

以下はAtlasで勧める実務上の記録例であり、PROVの必須項目一覧ではない。

| 段階 | 残すもの |
| --- | --- |
| 入力 | 出典URL、取得日、データの版、対象範囲、利用条件 |
| 処理 | 使用した道具と設定、CRS、抽出・結合条件、重複・欠損の扱い。コードを使った場合はその版と実行環境 |
| 出力 | 出力名、作成日、入力件数、対応済み一意件数、未所属・複数所属の件数 |
| 検証 | 期待値との照合結果、未確認の範囲、担当者や実行主体 |

原本と加工後のファイルを区別し、同じ処理へ戻れる対応を残す。記録がそろっていても、入力データや推計自体の正しさを保証するわけではない。公開する記録へAPIキーや個人の移動履歴を含めず、必要な参照情報とアクセス制御を分ける。

## 結果に添える短い説明例 { #result-note }

プログラムを作らなくても、地図や集計表に「何を数えたか」を添えられる。次は架空の例であり、実際の施設数を示さない。

> A駅周辺の指定範囲について、データBの版Cに収録されたカフェ相当のレコードを数えた。分類条件Dを使い、営業状態が不明なものも含めた。重複候補の扱いはEのとおり。現地の営業中店舗を全数確認した結果ではない。

B〜Eは実際に使った情報へ置き換える。分からない項目は「未確認」とし、取得日とデータの更新日を分けて記載する。提供元が変わった場合も、分析条件を変えた場合も、前回との差をたどる手掛かりになる。

## レコードと一緒に保持する情報

| 情報 | 確認したい内容 |
| --- | --- |
| 識別子 | 元の地物や過去の版との対応 |
| 出所・生成方法 | 現地測量、画像からの機械学習抽出など |
| 利用条件 | 再利用や他データとの組み合わせに関する制約 |
| 座標参照系 | 実世界の位置への対応 |
| 処理履歴 | 変換や属性追加の経緯 |

2026年9月17日のOvertureの記事は、GERSの永続ID、共通スキーマへの検証・統合、機械可読形式を関連付けている。すべての処理を通じてメタデータを保持することは同団体が示す目標であり、全レコードに必要な情報が揃っていることの保証ではない。

10月13日の解説は、異なる提供者の地物をGERSで対応付け、レジストリと変更履歴で継続的に追う考え方を補足する。同じ建物でも、概形だけが必要な用途と、高さや部材まで必要な用途がある。表現を一つに統一するより、同じ対象を指すと確認できることが重要になる。

入力元・受領日・版・検証結果を工程内で保持する説明は、公開ファイルの全属性にその履歴が含まれる保証ではない。分析に使う版の実際のフィールドと、識別子の変更記録を確かめる。

[Overtureのデータスキーマ](overture-schema.md)も参照。

自社の施設をOvertureの地物と一度照合すると、次の版でも共通IDで追跡できる。分割・統合ではIDが変わり得るため、前回結んだ相手が今も同じかを台帳と変更記録で確かめる。 [【OvertureMaps】GERSとは？ 地図の上の「もの」に背番号を付ける](https://note.com/pacificspatial/n/nf22c5b8b148b)（2026年11月5日確認）

## AIが見つけた情報を地図へ載せる前に

2026年10月7日の個人開発記事は、Next.js・MapLibre・OpenFreeMapで北朝鮮に関する公開資料を地図と表に整理し、4言語へ展開した例を紹介する。作者は、AIが存在しないURLや識別子を提示した経験から、原ページに記載があるか照合する処理を設けたと説明している。

出典・更新時点・確かさを地図上の情報と結び付ける設計は参考になる。ただし、単語や数字が原ページに存在するだけでは、その解釈や地物との対応が正しいことまで保証しない。地図と表で同じデータを参照する設計と、内容の事実確認を分ける。Atlasでは作者の説明を確認し、個々の施設・人物情報の検証やアプリの動作試験は行っていない。

## AI向けに自治体資料を集める基盤

Plotiは、自治体に分散した用途地域・許認可・所有権・洪水などの情報をAIから問い合わせるサービスである。公式ブログはMCP・REST API・CLIを提供し、不足データの収集依頼や変更追跡にも対応すると説明する。利用にはアカウントと対象データへの利用権限が必要になる。

2026年10月23日の報道は、同社の説明として57,818件の地域データセットの特定、40州での検索対応、1,823件の会議資料から20年分の採決記録を2.5日で復元した事例を伝える。これらは事業者の公表値で、第三者による精度・網羅率の検証ではない。

参考になるのは、AIが回答する前段の「資料を見つけ、取り込み、更新を追う」工程も扱う点である。出典が付くことと、PDFからの抽出や地番への対応が正しいことは別に確認する。元資料・取得日・対象地域・抽出した箇所を照合できる形で利用したい。日本の自治体への対応や本サービスの動作は今回確認していない。

## 地名の表記変更も来歴として残す

国土地理院は2026年10月30日、地名情報で取り扱う漢字の仕様を変更し、33文字を追加した。UTF-8で保存できることと、画面で正しく表示できること、旧表記と同じ地名として照合できることは別である。

例えば以前の代替表記と本来の漢字をそのまま比較すると、同じ場所でも別の文字列になる。元の地名は残し、検索用の正規化文字列、対応表の版、取得日を分けて記録すると、後から照合の理由を確認できる。地名だけで同一地点と決めず、識別子や位置も併用する。

紹介記事は保存・表示・文字数・照合を切り分けて確認している。ただし実データの更新前後の照合率を検証したものではない。本Atlasでも実地名データの比較は行っていない。
