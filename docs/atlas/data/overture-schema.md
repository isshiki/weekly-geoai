# Overtureのデータスキーマ

Overtureのスキーマは、地物の属性と制約を定義する。v2ではPythonのPydanticモデルを正本とし、データ検証と文書生成を共通の定義から行う。

## v2での構成

| 要素 | 役割 |
| --- | --- |
| `overture-schema` | 6テーマとツールをまとめて導入するパッケージ |
| Pydanticモデル | 型・制約の定義、属性の参照、データ検証 |
| 生成物 | JSON Schema、PySpark検証式、参照文書 |

GeoJSONとGeoParquetを扱うモデルであり、他形式への拡張可能性も説明されている。JSON Schema自体が廃止されるわけではない。

## 移行時の区別

2026年9月16日の記事は、約2週間前に公開したv2.0.0を説明している。記事公開日をリリース日として扱わない。YAML版の削除は2026年12月の予定で、追加フィールドを標準化するschema extensionsは次の目標である。

## データ・説明・検証の食い違いを減らす

データ本体、公開ポータル、別紙のデータ辞書をそれぞれ編集すると、列名や許容値の説明がずれる。2026年10月6日の公式解説は、型・許容値・説明・条件付き必須項目を共通モデルに置き、JSON Schema、Markdown文書、Python／CLI検証、PySparkの検査をそこから生成する設計を示す。

Pythonで実行できる独自の検証関数を書くだけでは、そのルールを文書や別の実行環境へ引き継げない。複数の出力で利用する制約は、生成側が読める形で定義する必要がある。共通化は定義の不一致を減らす方法であり、実世界でのデータの正確さまで保証するものではない。

## AIで仕様を移す場合の確認

同記事の著者は、AIに仕様を直接転記させると、許容値の脱落や根拠のない制約追加が起きたと報告する。固定した元資料を読み込んでモデルを生成する処理をAIに作らせ、再生成と差分比較で検査する方法を勧めている。生成処理自体の誤りも点検する。実装手順は出典へ案内し、ここでは仕様の正本と確認可能性を判断基準として扱う。
