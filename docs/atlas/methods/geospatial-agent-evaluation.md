# 地理空間AIエージェントの評価

たとえばAIに「駅から歩いて行ける公園を地図にして」と頼んだとする。完成した地図を開いたら、よく知っている公園を一つ選び、その入口までの道をたどってみよう。川の向こうの公園まで円の内側に入っているとき、AIは徒歩経路の代わりに直線距離を使ったのかもしれない。

## 評価する段階を分ける

| 段階 | 確認すること | 公園探しの例で見ると |
| --- | --- | --- |
| データ要件 | 必要なデータ一式と、地域・時期・解像度などの条件 | 駅、公園の入口、歩ける道路のデータがそろったか |
| 分析手順 | データを取得し、専門家が必要とする処理を進めたか | 出発する駅と徒歩時間を決め、道路に沿って調べたか |
| 最終結果 | 数値・地図が参照値や観測と合うか | 候補の公園を一つ選び、入口まで道がつながるか |

## モデル順位と実行環境を一緒に読む

Axis Spatialの評価サイトは、地理空間能力の総合指標と、モデル・実行環境・推論設定を組み合わせたエージェント指標を分ける。2026年11月7日時点の方法論1.0では、各問を1試行で採点し、数値・ファイル・形状はコード、地図などはAI判定を用いると説明している。

同じモデル名でも構成やText only／Text + visionの集計範囲が異なる。総合点だけで選ばず、目的に近い課題、実行環境、失敗を含む費用・時間を確認する。運営者も約3点未満の差をノイズの範囲として扱う。公開順位をあらゆる地域・業務の性能保証にしない。

[評価サイト](https://www.axisspatial.com/arena)、[方法論](https://www.axisspatial.com/arena/methodology)（2026-11-10本文確認）。本Atlasでは採点の再現や評価データ全件の監査は行っていない。

## データ要件を洗い出す力

GeoFitBench-LLMは48問で、時空間の関係と意味・地名の解釈を評価する。必要なデータ一式の特定と、用途に合う属性・条件の指定を分けて採点する。例題やタスク分解の指示なしで7モデルを比較し、GPT-5.4 Thinkingの一式特定成功率66.67％が最高だった。

これは分析実行の成功率ではない。暗黙の条件や曖昧な地名・時間表現に課題があり、実データの取得・分析までを検証する研究とも区別する。

## 専門ツールと計画の寄与

Google Earth AIのGRAは、Geminiと地理空間の専門スキル・ツールを組み合わせる研究システムである。必要なスキルを読み込み、大容量データは会話外に保持して参照し、最初に分析計画を作る。

論文は4構成・2モデル・4ベンチマークを比較した。GeoExpertQueriesのGemini 3.8 Flashでは、基本ツール付き3.3、専門ツール付き52.2、完全版62.7（100点満点）だった。主な改善は専門ツールの追加によるもので、事前計画の上積みはProや他の評価で一貫しなかった。

この採点は専門家の分析手順への適合であり、最終結果の正しさを保証しない。基本ツール側のPythonはネット接続なしという条件もある。著者らは出力を専門家が確認する初稿と位置付ける。本Atlasでは研究の評価結果を整理し、システムを再実行していない。

## 研究の評価と利用できる範囲を分ける

Googleの2026年10月14日の公式紹介は、CSV・GeoJSON・クラウド上の表などを持ち込み、地理空間の専門ツールと組み合わせる利用を示す。大容量データは専用の作業領域に置き、会話へ全件を詰め込まずに処理する。自分の地域データを使えることと、その地域で結果の正しさを検証したことは別である。

Ask Google Earthのdeep researchとA2A APIは申請制の初期・実験的アクセスである。公開されたGeoKTools・GeoExpertQueriesも開発用の分割であり、全評価データが公開済みとは解釈しない。専門家が出力を確認する初稿という位置付けは、活用事例の紹介でも保たれている。

## AutoGISの例で見る、AIが参照した資料と分析結果の確認

「AutoGIS」という名前の道具は二つある。どこから操作し、AIが何を手掛かりに処理を組み立てるのかが異なる。

- **THU-ESISの研究用基盤**では、Web画面やコマンドラインから依頼する。手元のデータを優先して探し、生成した分析コードを設定済みのQGISで実行する。例えば、ある地点の周囲を分析するときは、選ばれたデータと、コードが指定した距離・単位の両方を確かめられる。[研究チームのREADMEとデモ](https://github.com/THU-ESIS/AutoGIS)
- **sutharprin098のQGISプラグイン**では、QGISの中から操作する。1.0.3ではAIがコードを書く際にGISの実装資料を検索できるようになった。資料を参照できても、選んだ地域や分析条件が依頼に合うかは別途確かめる。[QGIS登録情報](https://plugins.qgis.org/plugins/AutoGIS/)・[1.0.3の変更履歴](https://plugins.qgis.org/plugins/AutoGIS/version/1.0.3/)

THU-ESISの研究では、113件のコード評価で、エラー記録だけを使った修正後の実行成功率は76.99％、入力データと処理関数の仕様も与えると94.69％だった（いずれも修正3回後）。出力地図が依頼に合うかは別に確かめる必要がある。 [AutoGIS: an agent framework for automated geospatial data management and analysis](https://www.tandfonline.com/doi/full/10.1080/17538947.2026.2704301)（2026年11月5日確認）

2026年11月5日に両者の公開資料を確認。動作や精度の比較は未実施。

## 自動化の速さは準備と結果を分けて比べる

TerraLabはQGIS 3.44.15で、ドイツ2都市の建物を地区別に集計する4方式を比較した。修正後は全方式が同社の検証基準を満たした。実行時間は次の通りで、モデル作成・コード執筆の時間は含まない。

| 方式 | ビーレフェルト | ミュンスター |
| --- | ---: | ---: |
| バッチ処理 | 62.0秒 | 39.8秒 |
| モデラー | 62.7秒 | 67.2秒 |
| PyQGIS | 8.1秒 | 7.4秒 |
| 自社AI Agent | 110秒 | 60秒 |

モデラーでは同名フィールドを取り違え、10地区のはずが1,058行になる出力も「成功」と表示された。地区数や面積の許容差など、実行前に決めた基準との照合が役立つ。方式ごとに処理の組み方も違うため、単純な製品速度ランキングにはしない。準備・修正・再利用の手間も、使う側の評価項目になる。[自動化比較](https://terra-lab.ai/blog/qgis-automation)

同社のClaude連携比較では、生成コードは2本とも初回失敗し、1本はURL修正後に成功した。ただしコード側はPune郡の14区分、AI Agent側は市の58選挙区を対象とし、MCPの結果は別都市の過去試行である。「同じ依頼文」でも同一条件の比較とは限らない。対象区域の意味を先にそろえる。[ClaudeとQGISの比較](https://terra-lab.ai/blog/claude-qgis)

## 地図風の画像と、データから作った地図を確かめる

TerraLabのレシフェでの実験では、画像モデル2種が描いた各10施設名のうち、OSMとの照合で「実在し駅から1km以内」を満たすものは0件だった。自社GISエージェントは88.7秒で公園50件・学校18件を抽出し、手動GIS処理とOSM IDが一致したと報告する。

確認できるのは指定データ・条件での一致であり、現地の全施設を把握した証明ではない。エージェントは中心部を2駅に限定し、施設名ラベルを付けず、PDF出力は著者が手動で行った。見た目、対象範囲、編集可能な成果物、保存完了を別々に確かめる。[地図生成の比較](https://terra-lab.ai/blog/ai-map-generator)

以上は自社AI製品の提供元による2026年11月7日公開の事例で、単一課題・少数試行から一般的な優劣は決められない。2026年11月8日に3記事の本文を確認。Atlasでの再実験は行っていない。

## 利用事例の短縮時間と正確性を分ける

Pacific Spatial Solutionsの解説とGoogleの公式紹介は、WHO AFRO等が森林減少・鉱山・人口を組み合わせ、48集落と4万5,500人超のリスク対象を数分で特定したと報告する。People in Needの過去14件のサイクロン経路分析も紹介する。これらは提供者・利用者による業務事例であり、独立した誤差測定や対象住民全員の個別確認を意味しない。時間短縮と、分析結果の正確性・専門家レビューを分けて評価する。
